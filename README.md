# نظام إدارة مرتجعات الموردين

تطبيق ويب (HTML + JavaScript، PWA) لإدارة مرتجعات الموردين، ربط أصناف الموردين بأصناف نظام ERP، تتبع تكلفة كل مورد وتاريخها، ودورة حياة كاملة للمرتجعة من المسودة حتى تسجيلها على ERP.

## التشغيل محليًا

الكود مبني على ES Modules، فمتصفحك مش هيشغّله بفتح `index.html` مباشرة (file://) — لازم سيرفر محلي بسيط:

```bash
python3 -m http.server 8080
# أو: npx serve
```

وبعدين افتح `http://localhost:8080`.

## الاختبارات

في مجموعة اختبارات بتفتح التطبيق في متصفح حقيقي وتمشي على كل الشاشات، وبتشتغل على **نسخة وهمية من قاعدة البيانات في الذاكرة** — يعني عمرها ما بتلمس بيانات Firestore الحقيقية.

```bash
npm install                                  # أول مرة بس
npx playwright install chromium              # أول مرة بس
npm test                                     # تشغيل الاختبارات
npm run lint                                 # فحص الكود
```

الاختبارات دي بتشتغل تلقائيًا في GitHub على كل رفعة على `main` وعلى كل Pull Request. **ولو وقعت، رقم الإصدار مش بيترفع** — يعني النسخة اللي فيها مشكلة مش بتتبعت تلقائيًا للأجهزة اللي فاتحة النظام.

## طريقة العمل: فرع ← فحص ← دمج ← نشر

أي تعديل — صغير أو كبير — بيمشي بنفس الطريق:

1. **الشغل كله على فرع**، مش على `main` مباشرة.
2. **Pull Request** على `main`. أول ما الـ PR يتفتح، الـ GitHub Action بيشغّل `npm run lint` و`npm test` عليه.
3. **الدمج بعد ما الفحوصات تعدّي** فقط. لو أي اختبار وقع، الـ PR بيفضل مفتوح لحد ما يتصلّح.
4. **النشر بيحصل بعد الدمج**: GitHub Pages بينشر من `main`، وبعدها الـ Action بيرفع رقم الإصدار فيوصل التحديث للأجهزة اللي فاتحة النظام.

ليه ده مهم: GitHub Pages بينشر من `main` **من غير ما يستنى الفحوصات**. يعني لو حاجة اترفعت على `main` مباشرة وفيها كسر، النسخة المكسورة بتبقى شغالة على الموقع لأي حد يعمل refresh — حتى لو الاختبارات وقعت بعد كده ومنعت رفع رقم الإصدار. لما الشغل كله يعدّي على فرع و PR، `main` مبيوصلهاش غير كود عدّى الفحوصات، وبكده النشر نفسه بيبقى مضمون مش رقم الإصدار بس.

الاستثناء الوحيد للرفع المباشر على `main` هو الـ commit اللي الـ Action نفسه بيعمله لرفع رقم الإصدار (بينتهي بـ `[skip ci]`).

**طريقة الدمج**: Squash أو merge commit، الاتنين شغالين. جوب رفع الإصدار بيدوّر على سطور `سجل:` في **كل الـ commits اللي الدمج جابهم**، مش في آخر commit بس، وكل سطر بيبقى بند لوحده في `CHANGELOG.md`. (قبل كده كان بيقرا آخر commit بس، فأول دمج بـ merge commit كتب في السجل "Merge pull request #2…" بالإنجليزي — ده اللي بقى مستحيل يحصل تاني.) لو بتفضّل تاريخ نضيف، الـ Squash بيخلي كل تعديل commit واحد على `main`.

ملحوظة: متحطش `[skip ci]` في رسالة commit بتاعك — GitHub بيلغي الـ workflow كله وقتها، يعني الاختبارات نفسها مش هتشتغل على الـ PR.

## الرفع على GitHub Pages

1. ارفع محتويات هذا المجلد لمستودع جديد على GitHub (اسم مقترح: `supplier-returns-system`).
2. من **Settings → Pages**: اختر **Deploy from a branch**، الفرع `main`، والمجلد `/ (root)`.
3. الموقع هيبقى متاح على `https://<username>.github.io/supplier-returns-system/`.

## رقم الإصدار والتحديث التلقائي

- رقم الإصدار الحالي ظاهر أسفل القائمة الجانبية في التطبيق.
- كل مرة يوصل commit جديد لـ `main` (يعني بعد دمج الـ PR)، الـ GitHub Action في `.github/workflows/bump-version-and-deploy.yml` بيرفع رقم الإصدار تلقائيًا (patch)، ويعدّل:
  - `js/core/version.js`
  - `version.json`
  - `sw.js` (اسم الكاش، عشان النسخة القديمة تتمسح من متصفح المستخدم)
  - `CHANGELOG.md`
  - ويعمل commit تاني تلقائيًا على `main`، فمش محتاج تعمل حاجة يدويًا.
  - رفع رقم الإصدار بيحصل **بعد** ما الاختبارات تنجح فقط.
  - نص السجل بيتاخد من سطر بيبدأ بـ `سجل:` في رسالة الـ commit. لو مفيش، بياخد عنوان الـ commit زي ما هو.
- التطبيق نفسه بيفحص `version.json` كل 5 دقائق (وكل مرة ترجع للتبويب)، ولو لقى رقم إصدار مختلف عن اللي شغال عندك، بيظهر رسالة ويعمل تحديث تلقائي (reload) بدون ما تعمل حاجة.
- **التحديث محدود بـ 3 محاولات**: أول محاولة إعادة تحميل عادية، والتانية بتمسح كاش الـ Service Worker، والتالتة بتحدّثه بالعافية. لو الـ 3 فشلوا، بيظهر شريط "حاول تاني" بدل ما التطبيق يفضل يعيد التحميل للأبد. الحلقة دي حصلت فعلًا في الإصدارات 1.17.x — تفاصيل السبب في تعليقات `sw.js` و`js/app.js`، والاختبار اللي بيحميها في `tests/update-recovery.mjs`.
- لو حبيت ترفع رقم إصدار **minor** أو **major** بدل الافتراضي (patch)، شغّل يدويًا قبل الـ push:
  ```bash
  node scripts/bump-version.js minor   # أو major
  ```

## الطباعة على ماكينة الكاشير الحرارية

خيار "طباعة إيصال حراري" في تصدير تقرير المرتجعة بيجهّز صفحة طباعة بعرض 80mm ويفتح شاشة الطباعة على طول (مش ملف Excel — ملفات Excel مش مصممة للطباعة على لفة حرارية ضيقة، فالحل العملي هو تنسيق طباعة مباشر بيتعرف عليه أي طابعة حرارية متصلة كطابعة عادية في نظام التشغيل).

الطباعة بتحصل من خلال `iframe` مخفي مش نافذة منبثقة، عشان متصفحات الموبايل بتمنع النوافذ المنبثقة افتراضيًا وده كان بيمنع الطباعة من التليفون. لو الطابعة عندك 58mm بدل 80mm، غيّر `size: 80mm auto;` في `openThermalPrintView` بملف `js/modules/return-export.js`.

## الشاشة الرئيسية

كل رقم على الشاشة الرئيسية بيوصّل للشاشة اللي جاي منها — البطاقات الأربعة وكل سطر في "تحتاج إجراء".

"تحتاج إجراء" بتعرض **بس** الحاجات اللي فيها شغل مستني فعلًا؛ لو كله صفر بتقول "مفيش حاجة محتاجة إجراء". وفيها بند لـ**المرتجعات اللي مستنية استلام البدائل** — التتبع ده موجود لكل صنف من إصدار 1.16.0 بس مكانش بيظهر في أي مكان.

الأرقام بتتحدّث كل دقيقة وانت فاتح الشاشة، وبتقف لما التبويب يبقى مخفي. ولو مفيش رقم اتغير، الشاشة مش بتترسم من الأول (مفيش رفرفة).

## عمود الباركود في التصدير

في شاشة تصدير المرتجعة، وفي شاشة مراجعة الفواتير، فيه خانة اختيار لعمود **الباركود**، **متعلّم عليها افتراضيًا** — شيل العلامة لو مش عايز الباركود في نسخة معيّنة.

الباركود بيتجاب من صنف الـ ERP المربوط بالسطر وقت التصدير نفسه، مش متخزّن نسخة في المرتجعة — فلو صلّحت باركود صنف، كل التصديرات الجديدة بتاخد الصح تلقائيًا. الأصناف غير المرتبطة بتظهر "—".

## مراجعة الفواتير وأصناف المورد

خانة الصنف في مراجعة الفواتير هي **"اسم الصنف عند المورد"** — نفس منطق المرتجعة بالظبط:

- بتقترحلك أصناف المورد اللي اخترته، وتحت كل واحد صنف ERP المربوط بيه وسعر القطعة الحالي.
- اختيار صنف بيملّي **سعر القطعة تلقائيًا** (محوّل للوحدة اللي مختارها — لو دستة بيضربه في 12).
- اسم جديد على المورد بيتضاف في **أصناف المورد** على طول، فأول ما تقابله في فاتورة يبقى جاهز في المرتجعة الجاية.
- السعر اللي بتكتبه بيتحوّل لسعر قطعة وبيتحفظ كتكلفة الصنف عند المورد — وبيطبّق على الأصناف اللي بنفس الاسم. بتظهرلك رسالة بتقولك التكلفة اتحدّثت لمين، فمفيش حاجة بتتغير من ورا ظهرك.

لازم تختار المورد الأول عشان الخانة دي تشتغل — من غيره مفيش أصناف تختار منها.

## تكلفة واحدة للاسم الواحد عند المورد

الاسم الواحد عند المورد ليه **سعر واحد**، حتى لو مربوط بأكتر من صنف ERP. المورد بيبيع "حجاب سوري" بسعر واحد — إنت اللي بتقسّمه عندك لأبيض وأسود. فتغيير التكلفة على أي واحد فيهم بيطبّق على كلهم، وأي صنف جديد تضيفه بنفس الاسم بيبدأ بنفس السعر تلقائيًا.

نافذة التكلفة بتقولك قبل ما تحفظ لو السعر مشترك مع أصناف تانية وكام واحد.

## تحديث تكلفة أصناف المرتجعة

تكلفة السطر في المرتجعة **بتتجمّد وقت ما تضيفه** — عشان تغيير سعر بعدين ما يعيدش كتابة مرتجعة اتبعتت خلاص. الوش التاني إن مسودة لسه شغال عليها بتفضل شايلة السعر القديم.

فبقى في زرارين، **بيظهروا بس على المرتجعات اللي لسه تنفع تتعدل** (مسودة أو مفتوحة للتعديل):

- **"↻ تحديث التكلفة"** فوق جدول الأصناف — بيجيب أحدث تكلفة لكل الأصناف مرة واحدة، وبيقولك كام صنف هيتغيّر قبل ما يأكد.
- **"↻"** جنب تكلفة كل صنف — لصنف واحد بس.

المرتجعات المرسلة والمؤرشفة مالهاش الزراير دي أصلًا، فتكلفتها التاريخية بتفضل زي ما هي.

## تكرار أصناف المورد

اللي بيحدد هوية صنف عند المورد هو **الاسم + صنف ERP المربوط بيه**، مش الاسم لوحده. المورد ممكن يسمّي حاجة واحدة باسم واحد وهي عندك بتتقسم على أكتر من صنف في ERP — فنفس الاسم ينفع يتسجّل أكتر من مرة طالما مربوط بأصناف ERP مختلفة.

- نفس الاسم + **نفس** صنف ERP → نفس السجل، مش بيتعمل نسخة.
- نفس الاسم + صنف ERP **مختلف** → سجل منفصل.
- اسم موجود ولسه **مش مربوط** → بيتربط هو، مش بيتعمل سجل جديد.
- في نافذة "إضافة / تعديل صنف عند المورد" فيه **شريط فوق بيقولك إنت بتعمل إيه دلوقتي**:
  - كتبت اسم من غير ما تختار اقتراح → صنف جديد، والقاعدة اللي فوق هي اللي بتحكم.
  - اخترت اقتراح → **"✏️ بتعدّل على صنف موجود"**، وأي تغيير (الربط، التكلفة) بيتطبّق على السجل ده.
  - جنبه زرار **"+ لأ، ضيف ربط ERP تاني"** → بيحوّلك لوضع **"➕ هتضيف ربط ERP تاني لنفس الصنف"**: الاسم والتكلفة بيفضلوا زي ما هما، وبيفضّيلك خانة ERP تختار منها الصنف الجديد، والحفظ بيعمل **سجل منفصل**. من غير اختيار صنف ERP جديد الحفظ بيترفض.

ولما تضيف صنف في مرتجعة وتختاره من الاقتراحات، السطر بيترتبط **بالسجل اللي اخترته بالظبط**. ولو كتبت اسم متسجّل أكتر من مرة من غير ما تختار، النظام بيرفض ويقولك تختار من القائمة — بدل ما يخمّن ويسجّل المرتجعة على صنف ERP غلط.

## الحماية من الضغط المزدوج

كل زرار بيضيف سجل بيتقفل أثناء التنفيذ (`submitOnce` في `js/core/utils.js`)، لأن الإضافة بتاخد رحلة للسحابة وده وقت كفاية إنك تضغط مرتين. اللي كان محمي: زرار الإضافة في المرتجعة، ومرتجعة/مراجعة جديدة. اللي **مكانش محمي واتصلح**: زرار الإضافة في مراجعة الفواتير (كان بيضيف السطر مرتين فعلًا)، وزرار الحفظ في "إضافة اسم صنف" (كان بيعمل السجل مرتين)، وزرار حفظ التكلفة.

## الوحدات (قطعة / دستة / أي وحدة تضيفها)

الوحدات متعرّفة في مكان واحد (`js/core/units.js`) وبتتعدّل من **مراجعة الفواتير ← إدارة الوحدات**، ونفس القائمة بتستخدم في كل مكان بتكتب فيه سعر. الافتراضي: قطعة (×1) ودستة (×12).

**تكلفة صنف المورد**: نافذة "التكلفة" فيها اختيار الوحدة جنب الخانة. اختار "دستة" واكتب سعر الدستة، والنظام بيحسب سعر القطعة ويحفظه — وبيوريك قبل ما تحفظ الرقم اللي هيتخزن بالظبط. تبديل الوحدة **بيعيد صياغة نفس التكلفة** مش بيعيد تفسير الرقم المكتوب: 77.50 بالقطعة بتبقى 930.00 بالدستة. اللي بيتخزن دايمًا هو **سعر القطعة**.

## الوحدة والسعر في مراجعة الفواتير

الوحدة اللي تختارها بتحدد **معنى السعر اللي بتكتبه**:

- اخترت **قطعة** → السعر اللي بتكتبه هو سعر القطعة.
- اخترت **دستة** → السعر اللي بتكتبه هو سعر الدستة، والنظام بيقسمه على 12 ويوريك **سعر القطعة** في عمود لوحده.

نفس الكلام على أي وحدة تضيفها بنفسك (كرتونة، نص دستة...) — بيتقسم على المضاعف اللي حطيته لها. الإجمالي مش بيتأثر (الكمية × سعر الوحدة)، اللي بيتحسب هو سعر القطعة عشان تقارنه بتكلفتك في ERP.

**عمود سعر القطعة مليان دايمًا** — حتى لو الصنف اتضاف بالقطعة (وقتها سعر القطعة هو نفسه السعر اللي كتبته). والشرطة "—" بتبقى في عمود سعر الوحدة، لأن صنف اتضاف بالقطعة أصلًا مالوش سعر دستة. كده مدخل البيانات عمره ما يلاقي خانة سعر القطعة فاضية ويفتكرها ناقصة.

اسم عمود سعر الوحدة بيتسمّى على الوحدة اللي الفاتورة مستخدماها فعلًا — **"سعر الدستة"** لو كلها بالدستة، ولو الفاتورة الواحدة فيها أكتر من وحدة كبيرة بيرجع لاسم عام.

## فلتر حالة المرتجعة

قائمة المرتجعات فيها فلتر **الحالة** جنب فلاتر المورد والتاريخ، بيغطي كل الحالات اللي النظام بيتابعها — مش بس الأربعة اللي في القائمة الجانبية:

كل المرتجعات · مسودة · النشطة · المرسلة · قيد التعديل بعد الإرسال · غير المسجلة على ERP · في انتظار استلام البدائل · الأرشيف

كل حالة ليها رابط خاص بيها (`#/returns/<key>`)، فتقدر تحفظها أو ترجعلها بزرار الرجوع. التعريفات كلها في `RETURN_FILTERS` بملف `js/modules/returns.js` — إضافة حالة جديدة بتظهر في الفلتر وبتتسجّل كصفحة تلقائيًا.

## القائمة الجانبية على الموبايل

القائمة بتاخد **مدخل خاص بيها في تاريخ التصفح** وهي مفتوحة، فزرار الرجوع في التليفون بيقفلها بس من غير ما يخرجك من الشاشة. والضغط على اسم الشاشة اللي إنت فيها بالفعل بيقفل القائمة ويعيد تحميل الشاشة (بدل ما مكانش بيعمل أي حاجة، لأن الـ hash مبيتغيرش فالراوتر مبيشتغلش).

## تاريخ التقرير المُصدَّر

التقرير (Excel، الصورة، الإيصال الحراري) بيكتب:

- **آخر تعديل** — طول ما المرتجعة مسودة، لأن دي الحاجة اللي بتتغير.
- **تاريخ الإرسال** — أول ما تتبعت للمورد، وبيحل محل تاريخ آخر تعديل تمامًا، لأن ده التاريخ اللي إنت والمورد هتتكلموا عنه.

## التصدير بيقرا الحالة الحالية

شاشة المرتجعة وشاشة مراجعة الفواتير **مش بيترسموا من الأول** لما تعدّل كمية أو سعر — ده مقصود عشان الكتابة تبقى سريعة (التعديل بيتكتب في قاعدة البيانات وبيتحدّث في الجدول على طول). ومعناه إن نسخة الأصناف اللي الشاشة اترسمت بيها بتبقى قديمة أول ما تكتب فيها.

عشان كده أي تصدير (Excel، صورة، واتساب، طباعة، نسخ كنص) بيعمل حاجتين قبل ما يشتغل:

1. **يستنى أي حفظ لسه شغال** — الضغط على زرار التصدير بيخرّجك من الخانة اللي بتكتب فيها وده بيبدأ الحفظ، والحفظ نفسه فيه تأخير نص ثانية. من غير الانتظار ده التصدير ممكن يسبق الحفظ.
2. **يقرا المرتجعة من قاعدة البيانات من جديد** بدل ما يستخدم النسخة القديمة.

الكود ده في `collectExportLines` (المرتجعات) و`loadReviewItemsWithBarcodes` + `exportWith` (مراجعة الفواتير)، والانتظار في `settle()` بملف `js/core/autosave.js`.

## صور التقارير

تنزيل التقرير كصورة (أو مشاركته على واتساب) بيرسم التقرير مباشرة على `canvas` في `js/modules/report-canvas.js`. الطريقة القديمة كانت بتستخدم مكتبة `html2canvas`، وهي بتعيد حساب مواضع الكلمات بنفسها وكانت بتشيل المسافات بين الكلمات العربية (فـ"اسم الصنف عند المورد" كانت بتطلع "اسمالصنفعندالمورد"). الرسم المباشر بيسيب تشكيل النص للمتصفح نفسه، وكمان بيخلي تصدير الصور شغال من غير إنترنت ومن غير أي مكتبة خارجية.

## المزامنة السحابية (Firebase)

النظام دلوقتي متصل بـ Firestore بدل التخزين المحلي فقط، فبيانات الموردين والمرتجعات والأصناف مشتركة بين أي جهاز يفتح نفس الرابط.

### إعداد لازم قبل أول تشغيل
1. **Firestore Database** لازم يكون متعمل من Firebase Console (Firestore Database → Create database).
2. **Anonymous Authentication** لازم يكون مفعّل: Console → Authentication → Sign-in method → فعّل **Anonymous**. النظام بيسجّل دخول تلقائي بدون أي شاشة تسجيل تظهر للمستخدم — ده اللي بيسمح لقواعد الأمان إنها تمنع أي حد بره النظام من قراءة أو تعديل البيانات.
3. **قواعد الأمان**: افتح ملف `firestore.rules` في هذا المشروع، انسخ محتواه، والصقه في Console → Firestore Database → Rules → Publish.

### أول مرة بعد التحديث
لو الجهاز ده كان عليه بيانات محلية قبل كده، النظام هيرفعها تلقائيًا لـ Firestore أول مرة يفتح فيها (مرة واحدة بس، ومش هيحصل تاني، ومش هيمسح حاجة). هتشوف رسالة تأكيد بعدد السجلات اللي اتنقلت. لو هتضيف جهاز تاني بعدين وعليه بيانات مختلفة، خد نسخة احتياطية منه الأول (من شاشة الإعدادات) قبل ما تفتح النظام عليه، عشان تقدر تدمج أي بيانات لو احتجت.

### ملاحظات مهمة
- **العمل بدون إنترنت**: شاشات العرض والتعديل بتشتغل أوفلاين عادي (Firestore بتحفظ نسخة محلية وتزامن تلقائي لما النت يرجع)، **ماعدا إنشاء مرتجعة جديدة برقم جديد** — ده محتاج اتصال إنترنت لحظة الإنشاء عشان رقم المرتجعة يتولّد بدون تعارض بين الأجهزة.
- **استيراد Excel لكميات ضخمة** (آلاف الأصناف): هيبقى أبطأ شوية من قبل لأنه بيكتب كل سجل على السحابة، وممكن يستهلك حصة الاستخدام المجاني اليومي لو الاستيراد ضخم جدًا.
- الأمان الحالي (Anonymous Auth) مناسب لجهاز/فريق موثوق بيه. لو حبيت لاحقًا تحدد مين بالظبط يقدر يدخل (يوزر وباسورد لكل شخص)، ده تطوير إضافي سهل نضيفه فوق نفس البنية.
